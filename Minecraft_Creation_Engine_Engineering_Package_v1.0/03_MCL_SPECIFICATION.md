# Minecraft Creation Language Specification

**Specification ID:** SPEC-004  
**Status:** Draft 0.1  
**Audience:** Engineering, AI/ML, QA, and Minecraft integration teams  
**Purpose:** Define the canonical structured language shared by the intent model, validator, state manager, deterministic generator, benchmark system, and verification harness.

---

# 1. Purpose

Minecraft Creation Language (MCL) is the internal representation of a Minecraft mod project.

Players do not write or see MCL during normal use. They communicate in English. The Intent Adapter translates English into MCL operations.

MCL is not Java, a scripting language, or a replacement for Minecraft APIs. It is a constrained declarative representation of supported gameplay intent.

The core contract is:

```text
English request
    ↓
MCL operations
    ↓
Validated candidate state
    ↓
Deterministic generation
    ↓
Verified Minecraft behavior
```

---

# 2. Design Rules

## MCL-001 — Declarative

MCL describes desired gameplay state, not implementation steps.

## MCL-002 — Stable

The language must change more slowly than generated Java or loader APIs.

## MCL-003 — Versioned

Every document and operation must identify its schema version.

## MCL-004 — Deterministic

The same validated state must produce the same generated implementation for the same target and generator version.

## MCL-005 — Typed

Concepts, properties, operations, triggers, conditions, and actions must use defined types.

## MCL-006 — Referentially safe

References must resolve to stable concept IDs or recognized vanilla Minecraft identifiers.

## MCL-007 — Transactional

Operations are applied to a candidate state and committed only after verification.

## MCL-008 — Capability bounded

A syntactically valid request may still be rejected when the current generator cannot implement it.

## MCL-009 — No hidden behavior

The generator must not add gameplay behavior not represented in canonical state or required by the platform.

## MCL-010 — No arbitrary code

The MVP MCL does not contain Java, Kotlin, scripts, shell commands, Gradle fragments, or free-form executable code.

# 4. Common Envelope

Every top-level MCL document must include:

```json
{
  "schema_version": "0.1.0",
  "document_type": "project",
  "document_id": "project-ruby-world",
  "revision": 1
}
```

## Required fields

| Field | Type | Meaning |
|---|---|---|
| `schema_version` | string | MCL schema version |
| `document_type` | enum | Document category |
| `document_id` | string | Stable document identity |
| `revision` | integer | Monotonic document revision |

Optional metadata:

```json
{
  "created_at": "2026-07-17T12:00:00Z",
  "updated_at": "2026-07-17T12:05:00Z",
  "created_by_transaction": "tx-000001",
  "updated_by_transaction": "tx-000002"
}
```

Timestamps are metadata and must not affect deterministic generation.

# 5. Identifier Rules

MCL uses three identifier forms.

## 5.1 Stable MCL ID

Internal immutable identity:

```text
concept-01JY...
recipe-01JY...
behavior-01JY...
tx-000001
```

Requirements:

- globally unique within the project;
- immutable after creation;
- never derived solely from the display name;
- generated by the state manager, not trusted from model output.

## 5.2 Minecraft namespace ID

Generated Minecraft registry identity:

```text
mce_ruby_world:ruby_blade
```

Format:

```text
namespace:path
```

Constraints:

- lowercase;
- ASCII;
- underscores permitted;
- validated against Minecraft resource-location rules;
- unique in the project;
- stable unless explicitly renamed through an operation that changes registry identity.

Changing a display name does not automatically change the namespace ID.

## 5.3 Display name

Player-facing text:

```text
Ruby Blade
```

Display names may change without changing stable identity.

# 6. References

A reference may identify:

- an MCL stable ID;
- a namespace ID;
- a unique display name;
- a unique alias;
- a supported contextual selector;
- a vanilla Minecraft ID.

## Preferred canonical form

```json
{
  "reference_type": "concept_id",
  "value": "concept-01JY..."
}
```

## Intent-stage reference

The model may emit:

```json
{
  "reference_type": "display_name",
  "value": "Ruby Blade"
}
```

The validator and resolver must normalize it to a stable ID before state mutation.

## Supported contextual selectors

```text
last_created_concept
last_modified_concept
only_weapon
only_block
only_item
```

Selectors that resolve to zero or multiple targets require clarification.

## Vanilla reference

```json
{
  "reference_type": "minecraft_id",
  "value": "minecraft:stick"
}
```

# 8. Concept Base Object

All concepts use this structure:

```json
{
  "schema_version": "0.1.0",
  "document_type": "concept",
  "document_id": "concept-ruby-blade",
  "revision": 2,
  "concept": {
    "concept_id": "concept-ruby-blade",
    "namespace_id": "mce_ruby_world:ruby_blade",
    "concept_type": "weapon",
    "subtype": "sword",
    "display_name": "Ruby Blade",
    "description": "A durable ruby sword.",
    "aliases": [
      "ruby sword"
    ],
    "properties": {},
    "appearance_id": "appearance-ruby-blade",
    "tags": [],
    "status": "active"
  }
}
```

## Common fields

| Field | Required | Meaning |
|---|---:|---|
| `concept_id` | yes | Stable identity |
| `namespace_id` | yes | Minecraft registry identity |
| `concept_type` | yes | High-level type |
| `subtype` | conditional | Specific supported subtype |
| `display_name` | yes | Player-facing name |
| `description` | no | Player-facing description |
| `aliases` | no | Natural-language references |
| `properties` | yes | Typed property object |
| `appearance_id` | no | Appearance reference |
| `tags` | no | Structured grouping |
| `status` | yes | `active` or `deleted` |

Deleted concepts remain in transaction history but are not generated.

# 10. Item Properties

Example:

```json
{
  "max_stack_size": 64,
  "fire_resistant": false,
  "rarity": "common",
  "creative_tab": "ingredients"
}
```

Constraints:

| Property | Type | Constraint |
|---|---|---|
| `max_stack_size` | integer | 1–64 |
| `fire_resistant` | boolean | any |
| `rarity` | enum | common, uncommon, rare, epic |
| `creative_tab` | string/enum | supported tab identifier |

An ingredient normally defaults to stack size 64 unless otherwise specified.

# 11. Weapon Properties

Example:

```json
{
  "attack_damage": 9.0,
  "attack_speed": -2.4,
  "durability": 1200,
  "repair_material": {
    "reference_type": "concept_id",
    "value": "concept-ruby"
  },
  "enchantability": 14,
  "max_stack_size": 1
}
```

Constraints:

| Property | Type | MVP constraint |
|---|---|---|
| `attack_damage` | number | greater than 0 |
| `attack_speed` | number | supported generator range |
| `durability` | integer | greater than 0 |
| `repair_material` | reference | valid item or tag |
| `enchantability` | integer | 0 or greater |
| `max_stack_size` | integer | must equal 1 |

Relative English terms such as “stronger,” “slower,” and “more durable” must be resolved by the Intent Adapter into explicit values or clarification.

Relative changes must never be stored as unresolved words.

# 18. Behavior Document

Example:

```json

  "schema_version": "0.1.0",
  "document_type": "behavior",

      "reference_type": "concept_id",

      "type": "player_hits_entity"

        "type": "random_chance",
```


# 21. Update Concept Operation

```json
{
  "schema_version": "0.1.0",
  "operation": "update_concept",
  "request_id": "req-002",
  "payload": {
    "target": {
      "reference_type": "display_name",
      "value": "Ruby Blade"
    },

      "properties": {
        "attack_speed": -2.8,
        "durability": 1500
      }
    }
  }
```

A missing field means no change.

Setting a field to `null` removes it only when that field is optional and the schema permits removal.

# 33. Validation Sequence

Operations must pass validation in this order:

```text
1. JSON parsing
2. Operation schema
3. Reference resolution
4. Property constraints
5. Semantic constraints
6. Capability constraints
7. Candidate-state schema
8. Candidate-state referential integrity
```

Failure at any stage stops candidate generation.

Validation errors must identify:

- error code;
- operation;
- path;
- message;
- repairability;
- owning component;
- clarification option where applicable.

---

# 34. Normalization

Before state mutation, the core normalizes:

- display-name and alias references to stable IDs;
- integer and decimal forms;
- color names to supported palette values;
- relative concepts to explicit values;
- vanilla aliases to Minecraft IDs;
- namespace hints to legal paths;
- omitted defaults;
- contextual selectors.

Example:

```text
"two rubies and a stick"
```

becomes explicit recipe counts and references.

The normalized operation is preserved in the transaction record.

---

# 35. Defaults

Defaults must be defined by schema version and concept subtype.

Example weapon defaults:

```json
{
  "max_stack_size": 1,
  "fire_resistant": false,
  "rarity": "common"
}
```

Defaults may not depend on nondeterministic model behavior.

The generator may apply platform-required implementation defaults, but gameplay-relevant defaults must be represented in normalized state or the schema specification.

---

# 36. Relative Language Policy

The Intent Adapter must convert relative language into explicit changes.

Examples:

```text
"slightly slower"
"much stronger"
"more durable"
"darker"
```

Resolution may use:

- documented adjustment rules;
- current concept values;
- vanilla comparison baselines;
- clarification.

Example adjustment rule:

```text
slightly slower attack speed
→ subtract configured small-step value
```

All relative-resolution rules must be versioned and unit tested.

The MCL state stores only the resulting explicit value and optional provenance metadata.

---

# 37. Partial Request Policy

A request may contain:

- fully supported intent;
- ambiguous intent;
- unsupported intent.

The Intent Adapter must return a structured partition:

```json
{
  "supported_operations": [],
  "clarifications": [],
  "unsupported_portions": []
}
```

No state mutation occurs until material clarifications and partial-execution choices are resolved.

---

# 38. Schema Evolution

Every MCL schema change must be classified as:

```text
patch
minor
major
```

## Patch

Clarifications or validation tightening without changing valid document meaning.

## Minor

Backward-compatible fields, operations, concepts, or enum values.

## Major

Breaking semantic or structural changes.

Projects must record their MCL schema version.

Migration code is not required for the first MVP release, but the state manager must reject unsupported future or incompatible versions clearly.

# 40. Fine-Tuning Contract

The fine-tuned model is trained to emit operation documents, not canonical state documents.

Each training example must include:

```json
{
  "case_id": "FT-WEAPON-001",
  "initial_state_fixture": "empty_project",
  "request": "Create a ruby sword called Ruby Blade with 1200 durability.",
  "expected_output": {
    "operations": [
      {
        "operation": "create_concept",
        "payload": {
          "concept_type": "weapon",
          "subtype": "sword",
          "display_name": "Ruby Blade",
          "properties": {
            "durability": 1200
          }
        }
      }
    ]
  }
}
```

The expected model output should omit system-assigned stable IDs.

Fine-tuning tests must compare:

- operation sequence;
- required payload fields;
- forbidden extra operations;
- reference intent;
- clarification status;
- unsupported status;
- mutation status.

Exact JSON string equality is not required when semantically equivalent field order differs.

---

# 41. End-to-End Contract

For every accepted English request, the system must preserve this trace:

```text
request text
→ raw model operations
→ normalized operations
→ candidate state
→ generated manifest
→ build result
→ verification requirements
→ verification report
→ committed transaction
```

Each artifact must reference the request ID and transaction ID.

This trace is required for:

- debugging;
- fine-tuning iteration;
- regression analysis;
- reproducibility;
- engineering accountability.

# 43. MVP Completion Criteria for MCL

The MCL implementation is complete enough for the MVP when:

1. all required operation schemas exist;
2. all MVP concept schemas exist;
3. reference resolution is deterministic;
4. candidate transactions are atomic;
5. generator capabilities can be validated;
6. every mutating operation creates verification requirements;
7. training examples can be validated against the same schemas;
8. unit tests can compare semantic operation output;
9. full-loop tests can trace English to verified behavior;
10. no arbitrary code can enter canonical state.
